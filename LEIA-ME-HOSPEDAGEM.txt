ZUPPO — CLOUDFLARE WORKERS

Antes de publicar, execute supabase/migrations/202610290003_catalog_queries.sql no projeto Supabase atual. A migração é reexecutável e não exclui dados. Não reexecute001/002.

Build: npm ci --include=dev && npm run build
Deploy: npm run deploy
Node.js22.13+

O wrangler.jsonc incluído aponta para Worker zuppo-site e bucket R2 zuppo, conforme informado. Confira a conta correta ao publicar. São obrigatórios ASSETS (binding de assets), BUCKET (R2), fallback SPA e run_worker_first:true. O Worker não embute mais os arquivos do frontend.

Se não há configuração, defina R2_BUCKET_NAME no ambiente de deploy. Opcional ZUPPO_WORKER_NAME (padrão zuppo-site). O script gera configuração ignorada em .wrangler/. Ele não grava segredos.

Runtime: CATALOG_PROVIDER=supabase, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY.
O exemplo inclui bindings gerenciados de contenção de requisições; sem eles, o fallback é limitado por isolate. Ajuste às condições da sua conta.

Preserve os dados R2 existentes; eles não estão no ZIP. Código, testes, migrações e documentação estão incluídos; node_modules, dados locais e credenciais não.

Teste /healthz, /api/offers?limit=12, login, rascunho/publicação, mídia e home. APIs devem retornar JSON.
Detalhes: docs/refinamento.md. Não é necessária migração de hospedagem para Render.
